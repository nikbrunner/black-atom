Rebuild the Theme Catalog from source truth

Outcome

Produce a coherent Catalog of 7 Collections and 32 existing Themes from the source Catalog on main. Preserve every selected Theme’s colors, make construction local and explicit, regenerate all adapters, align Monitor and Livery, and reconcile dots against the monorepo. The Minium Collection reserves a third future Theme whose background-led name and colors remain open.

Intent and limits

Must be true

  • The selected source Themes retain Primaries, Palette, Accents, Feedback, UI, and Syntax values.
  • Each Theme Definition owns its Primaries and chooses every derived namespace locally.
  • Catalog keys, generated outputs, Monitor, Livery, CLI, docs, and dots agree on the approved target Catalog.
  • Generated output and external links contain no stale managed Theme.

Operating boundaries

  • The rebuild changes structure and names, not source colors. The future third Minium Theme is the only planned new color design.
  • Color creators receive only the resolved namespaces they need; defineCollection assembles the final Theme metadata.
  • Generated files come from the generator, and Livery validation uses a temporary $HOME.
  • Git actions happen only when the owner requests them explicitly.

Starting point and execution model

The owner creates a fresh implementation branch directly from the repository’s normal main branch after approving this plan. This HTML is the implementation contract for the target structure; the current repository state is established separately before each slice begins.

03

Collection modules define the catalog contract

Architecture contract

Each Theme file defines only its resolved color namespaces through defineThemeColors. Each Collection module owns the Collection metadata and its typed Theme map through defineCollection. The root Catalog aggregates the complete Collection objects and derives its public key types from one typed Tuple of those imports.

Collection-to-Theme source structure
core/src/ ├── types/theme.ts └── themes/ ├── catalog.ts ├── define-collection.ts ├── define-theme-colors.ts ├── __fixtures__/source-colors.json ├── default/ │ ├── mod.ts │ └── black-atom-default-dark.ts ├── jpn/ │ ├── mod.ts │ └── black-atom-jpn-koyo-yoru.ts └── ...// ├── mod.ts └── .ts
File group Final responsibility
themes/<collection>/<theme>.ts Defines the Theme’s Primaries and color creators with defineThemeColors({...}). Exports resolved Theme.Colors; it does not own Collection metadata.
themes/<collection>/mod.ts Imports the Theme color objects and calls defineCollection({...}) once. The returned object contains inline Collection metadata and the typed Theme map, then becomes the module’s only export.
themes/define-theme-colors.ts Resolves color namespace objects and creators in the fixed order Primaries → Accents → Palette → Feedback → UI/Syntax. Creators receive the namespaces resolved before them and the function returns finished Theme.Colors.
themes/define-collection.ts Combines Collection metadata with each Theme’s local name, appearance, status, and resolved colors. It injects the Theme key, display label, and Collection metadata into the finished ThemeDefinition.
themes/catalog.ts Stores imported Collection objects in one as const Tuple. It derives Collection keys, Theme keys, Collection metadata, and per-Collection Theme keys from that Tuple, then exposes the hierarchical Collection inputs and flat Theme projection.
types/theme.ts Exports the public ThemeDefinition, CollectionDefinition, namespace types, and aliases for the Catalog-derived key and metadata types.
source-colors.json + theme tests Preserves the source payload and proves color equality, finished Collection assembly, and Collection-scoped Theme-key typing.
Theme file · target inline-creator shape after migration
import { defineThemeColors } from "../define-theme-colors.ts";
import createUi from "./create-ui-dark.ts";
import createSyntax from "./create-syntax-dark.ts";

const colors = defineThemeColors({
  primaries: {
    /* complete Primary scale */
  },
  accents: ({ primaries }) => ({
    a10: primaries.l10,
    a20: primaries.l20,
  }),
  palette: ({ primaries, accents }) => ({
    black: primaries.d40,
    cyan: accents.a10,
    /* complete Palette mapping */
  }),
  feedback: ({ palette }) => ({
    negative: palette.red,
    success: palette.green,
    info: palette.blue,
    warning: palette.yellow,
  }),
  ui: ({ primaries, accents, palette, feedback }) =>
    createUi({ primaries, accents, palette, feedback }),
  syntax: ({ primaries, accents, palette, feedback }) =>
    createSyntax({ primaries, accents, palette, feedback }),
});

export default colors;

defineThemeColors contract

  • The input contains Primaries and each derived color namespace as either a finished value or a creator.
  • Each derived namespace may be a value or an inline creator function. The creator receives the namespaces resolved before it.
  • Resolution order is Primaries → Accents → Palette → Feedback → UI/Syntax.
  • defineThemeColors invokes those creators in order and collects the results into one typed Theme.Colors object; it does not add Theme metadata.
  • Slice 1 proves this resolver contract; later Theme migration moves the current local resolutions into these inline creator properties.

defineCollection contract

  • The input contains Collection metadata and a Theme map whose values pair local Theme metadata with resolved color objects.
  • The function preserves the concrete Collection and Theme keys in its return type.
  • It injects the Theme key, display label, and Collection metadata into each finished ThemeDefinition.
  • The Collection module exports this one complete Collection object.
core/src/themes/catalog.ts · typed Collection aggregation
const collections = [
  defaultCollection,
  jpnCollection,
  terraCollection,
  stationsCollection,
  mnmlCollection,
  paperCollection,
] as const;

type CatalogCollection = (typeof collections)[number];
type KeysOf<T> = T extends unknown ? keyof T : never;

export type CatalogCollectionKey = CatalogCollection["meta"]["key"];
export type CatalogThemeKey = KeysOf<CatalogCollection["themes"]>;
export type CatalogCollectionMeta = CatalogCollection["meta"];

type CollectionForKey<C extends CatalogCollectionKey> = Extract<
  CatalogCollection,
  { meta: { key: C } }
>;

export type CatalogThemeKeysForCollection<C extends CatalogCollectionKey> =
  keyof CollectionForKey<C>["themes"];
Property Accepted value Creator receives
primaries Theme.Primaries Explicit inline object; no creator
accents Theme.Accents or creator { primaries }
palette Theme.Palette or inline creator { primaries, accents }
feedback Theme.Feedback or creator { primaries, accents, palette }
ui Theme.Ui or creator Full resolved color context
syntax Theme.Syntax or creator Full resolved color context

Creator context

Appearance-specific palette, Feedback, UI, and Syntax creators may remain in Collection folders and be imported by Theme files. Their signatures use the smallest applicable slice of Theme.Colors; defineThemeColors passes that context into the inline creator properties.

05

Outcome-oriented slices

Review and commit cadence

The Visual Plan execution procedure runs in three bounded subagent-driven runs. Progress markers below describe the current working branch and are checked exploratively before each next run. Run 1 implements Slice 1 with the commit gate enabled. Run 2 implements Slice 2 with the commit gate enabled. Run 3 implements Slices 3–5 with the commit gate disabled and no intermediate commit gates. Live dots reconciliation keeps its separate safety gate.

Slice 1 · ✓ complete

Prepare the shared foundation

Capture the 32-key source fixture and establish the Theme.* type shape, defineThemeColors context contract, defineCollection assembly contract, typed Collection Tuple, and creator-context tests.

Done when the fixture is exact and the contracts prove fixed color resolution, object/creator inputs, typed Collection and Theme keys, finished Theme data, and Collection-scoped key narrowing. Then stop at the Slice 1 commit gate.

Slice 2 · ✓ complete

Rebuild DEFAULT

Use the shared foundation to migrate the four DEFAULT Theme files to the inline-creator defineThemeColors({...}) shape and assemble them through the DEFAULT defineCollection module.

Done when all four Themes match their mapped source fixture entries and demonstrate the uniform shape. Then stop at the Slice 2 commit gate.

Slice 3 · ◐ partial

Complete the 7/32 Core Catalog

Construct every remaining Theme with the same inline-creator defineThemeColors({...}) shape. Split the former MNML group into Minium, JPN/Sanshoku, and the remaining target Collections; apply the Viridian and Polymer names; then align Collection modules, canonical keys, metadata, order, and default.

Done when all 32 targets match the fixture and only the target Catalog remains in Core.

Slice 4 · ◐ partial

Regenerate and align consumers

Generate all adapters from source, then align Monitor, Livery, CLI, fixtures, bindings, docs, and skills with the renamed target keys.

Done when generated path inventories are exact, generation is stable, Livery builds, and every consumer uses the current key set.

Slice 5 · ○ open

Reconcile dots behind the live-system gate

On the owner-provided dots branch, point discovery at the monorepo, update the registry and selected keys, and reconcile managed links in fixtures first.

Done when fixture runs are safe and idempotent. Real-home reconciliation happens only after explicit owner confirmation.

Live-system gate

All Livery validation uses temporary HOME, XDG_CONFIG_HOME, and XDG_DATA_HOME. Fixture-tested dots reconciliation may touch real links only after the owner sees the dry run and confirms it. Unrelated files and links are never pruning candidates.
